# Module 01 — Computing Foundations

# Chapter 01.08 — Computer Interconnects, PCIe, DMA, Interrupts, and I/O Architecture

## 1. Purpose of This Chapter

A processor does not operate in isolation. It must exchange data with memory, storage devices, network interfaces, graphics processors, accelerators, and other controllers. These transfers are coordinated through interconnects, device controllers, drivers, queues, interrupts, and direct memory access.

For a DevOps Architect, I/O architecture explains why an application can be slow while CPU utilization is low, why a fast storage device may be constrained by an interface, why network throughput depends on interrupt handling, and why virtual machines and containers can experience contention below the operating-system layer.

## 2. Learning Objectives

After completing this chapter, you should be able to:

- Explain the purpose of system interconnects.
- Distinguish data, address, and control communication conceptually.
- Describe PCI Express topology, lanes, links, and generations.
- Explain the roles of device controllers, firmware, and drivers.
- Compare polling, programmed I/O, interrupt-driven I/O, and DMA.
- Explain buffering, queues, batching, and backpressure.
- Relate I/O architecture to storage, networking, GPUs, virtualization, and cloud platforms.
- Diagnose interrupt saturation, bus constraints, queue buildup, and device contention.

## 3. The I/O Problem

Processors execute instructions much faster than many external devices can respond. I/O architecture exists to coordinate components with different speeds, protocols, and responsibilities.

A complete I/O path may include:

1. Application
2. Operating-system API
3. Kernel subsystem
4. Device driver
5. Device controller
6. System interconnect
7. Peripheral device
8. Completion notification

## 4. System Interconnects

An interconnect carries information among system components.

Conceptual categories include:

- Data transfer
- Address selection
- Control and status signaling

Older architectures were often described as shared buses. Modern systems commonly use switched point-to-point links and internal fabrics.

## 5. Shared Bus vs Switched Fabric

### Shared Bus

Multiple devices share one communication path.

Advantages:

- Simpler design
- Lower implementation cost

Limitations:

- Contention
- Limited scalability
- Shared bandwidth

### Switched Fabric

Devices communicate through dedicated or switched links.

Advantages:

- Higher aggregate bandwidth
- Better parallelism
- Improved scalability

PCI Express is a switched point-to-point architecture.

## 6. Bandwidth, Latency, and Contention

### Bandwidth

Amount of data transferable per unit time.

### Latency

Time required for a request or transfer to complete.

### Contention

Competition among devices or workloads for shared resources.

A high-bandwidth link can still have poor latency, and a low-latency device can still be constrained by shared bandwidth.

## 7. PCI Express

PCI Express, or PCIe, connects processors and chipsets to devices such as:

- NVMe drives
- Network adapters
- GPUs
- Accelerators
- Storage controllers

PCIe uses serial point-to-point links organized into lanes.

## 8. PCIe Lanes and Links

A PCIe link may use:

- x1
- x2
- x4
- x8
- x16

More lanes generally provide more bandwidth.

A device can be limited when:

- It has fewer active lanes than expected.
- It operates at an older negotiated generation.
- Multiple devices share an upstream link.
- The CPU or chipset topology constrains traffic.

## 9. PCIe Generations

Each PCIe generation increases per-lane transfer capability.

Architectural decisions should consider:

- Device generation
- Host generation
- Lane count
- Slot wiring
- Upstream topology
- Protocol overhead

A newer device installed in an older slot operates at the mutually supported capability.

## 10. Root Complex, Switches, and Endpoints

### Root Complex

Connects the processor and memory subsystem to PCIe.

### PCIe Switch

Expands connectivity and routes traffic among links.

### Endpoint

A device such as a network adapter, NVMe drive, or GPU.

Topology matters because devices may share bandwidth or traverse additional components.

## 11. Device Controllers

A controller translates operating-system commands into device-specific operations.

Examples include:

- Storage controller
- Network interface controller
- USB controller
- GPU controller

Controllers may provide:

- Queues
- Caches
- Error handling
- Offload features
- DMA engines

## 12. Firmware and Drivers

### Firmware

Code running on or close to the device.

### Driver

Operating-system software that controls the device and exposes a standard interface to the kernel.

A device can fail or perform poorly because of:

- Driver defects
- Firmware defects
- Version incompatibility
- Unsupported features
- Incorrect configuration

## 13. Memory-Mapped I/O

Memory-mapped I/O exposes device registers within the processor's address space.

The processor reads or writes specific addresses to configure the device or inspect status.

These addresses represent device control regions rather than ordinary RAM.

## 14. Programmed I/O

In programmed I/O, the processor actively moves data or repeatedly checks device status.

This is simple but consumes processor time and scales poorly for large transfers.

## 15. Polling

Polling repeatedly asks whether a device or event is ready.

Advantages:

- Predictable control
- Useful for very low-latency or high-rate workloads

Disadvantages:

- Wastes CPU when events are infrequent
- Can increase power consumption

Polling is sometimes preferred in specialized networking or storage workloads where interrupt overhead would be greater.

## 16. Interrupt-Driven I/O

A device generates an interrupt when it needs processor attention or completes work.

Typical flow:

1. The operating system submits an operation.
2. The device performs the work.
3. The device signals an interrupt.
4. The processor runs an interrupt handler.
5. The kernel completes the request.
6. The waiting application is notified.

## 17. Interrupt Handlers

Interrupt handling is divided into urgent and deferred work in many operating systems.

The immediate handler should do minimal work, while additional processing is deferred to reduce blocking of other interrupts.

High interrupt rates can consume substantial CPU capacity.

## 18. Interrupt Affinity

Interrupt affinity controls which processors handle specific interrupts.

Poor distribution can produce:

- One saturated CPU
- Uneven network processing
- Cache inefficiency
- Higher latency

Balancing must account for device queues, NUMA locality, and application placement.

## 19. Interrupt Coalescing

A device can combine multiple events before interrupting the processor.

Benefits:

- Lower interrupt overhead
- Better throughput

Trade-off:

- Increased per-event latency

The correct setting depends on whether the workload prioritizes latency or throughput.

## 20. Direct Memory Access

DMA allows a device to transfer data directly between the device and main memory without requiring the processor to copy every byte.

Typical flow:

1. The processor configures a transfer.
2. The DMA-capable device moves data.
3. The device signals completion.

DMA reduces CPU overhead and improves throughput.

## 21. DMA and Security

A DMA-capable device can access memory, creating security risk if uncontrolled.

An I/O memory-management unit, or IOMMU, restricts and translates device memory access.

IOMMU capabilities support:

- Isolation
- Safe device assignment
- Virtualization
- Protection from unauthorized DMA

## 22. Scatter-Gather I/O

Scatter-gather allows a device to transfer data across multiple noncontiguous memory regions in one logical operation.

This reduces copying and improves efficiency for networking and storage.

## 23. Buffers

A buffer temporarily holds data while components operate at different speeds.

Buffers are used in:

- Network receive and transmit paths
- Storage queues
- Application streams
- Device controllers

Too little buffering can reduce throughput. Too much buffering can increase latency and hide congestion.

## 24. Bufferbloat

Bufferbloat occurs when oversized queues retain excessive data, causing high latency even when packets or operations are not lost.

This is common in network paths but the principle applies to storage and application queues as well.

## 25. Queues

Modern devices use queues to support concurrency and parallelism.

Examples:

- NVMe submission and completion queues
- Network receive and transmit queues
- Storage request queues

Queue depth should be high enough to utilize the device but not so high that latency becomes unacceptable.

## 26. Batching

Batching combines several operations to reduce per-operation overhead.

Benefits:

- Higher throughput
- Fewer interrupts or system calls

Trade-off:

- Additional waiting time
- Larger failure scope

## 27. Backpressure

Backpressure prevents a fast producer from overwhelming a slower consumer.

Without backpressure, queues may grow until memory, latency, or reliability limits are exceeded.

Examples include:

- Network socket buffers
- Message queues
- Disk-write queues
- Application worker pools

## 28. Device Offload

Devices can perform work that would otherwise consume CPU.

Network examples:

- Checksum offload
- Segmentation offload
- Receive-side scaling
- Encryption offload

Storage examples:

- RAID calculations
- Compression
- Encryption

Offload can improve throughput but may complicate observability and troubleshooting.

## 29. Network Interface Architecture

A network interface commonly includes:

- Receive and transmit queues
- DMA engines
- Interrupt or polling mechanisms
- Offload features
- Driver

Packet processing may involve CPU, memory bandwidth, queues, and PCIe bandwidth simultaneously.

## 30. Storage Device Architecture

An NVMe path may include:

- Application or database
- Filesystem or direct I/O
- Kernel block layer
- NVMe driver
- Submission queue
- PCIe link
- Device controller
- Flash media
- Completion queue
- Interrupt

A bottleneck can appear at any stage.

## 31. GPUs and Accelerators

GPUs and AI accelerators transfer data through high-bandwidth interconnects.

Performance depends on:

- Device compute capability
- PCIe or specialized link bandwidth
- Host memory bandwidth
- Data-transfer frequency
- Batch size
- Software compatibility

A powerful accelerator may remain underutilized when data transfer is the bottleneck.

## 32. I/O and NUMA

Devices are often physically closer to a particular processor socket or NUMA node.

Remote memory or cross-socket traffic can increase latency and consume interconnect bandwidth.

High-performance workloads may require alignment of:

- Application threads
- Memory allocation
- Device interrupts
- Device locality

## 33. Virtualization of I/O

Virtual machines can access I/O through:

- Emulated devices
- Paravirtualized drivers
- Virtual functions
- Direct device passthrough

Each model trades portability, isolation, performance, and operational flexibility.

## 34. SR-IOV

Single Root I/O Virtualization allows a physical PCIe device to expose multiple virtual functions.

Benefits:

- Lower virtualization overhead
- Higher throughput
- Lower latency

Trade-offs:

- Greater configuration complexity
- Reduced mobility in some environments
- More direct hardware dependency

## 35. Device Passthrough

Passthrough assigns a physical device directly to a virtual machine.

Useful for:

- GPUs
- High-performance networking
- Specialized accelerators

Trade-offs include reduced sharing, scheduling flexibility, and migration options.

## 36. Containers and I/O

Containers share the host kernel and device infrastructure.

Container I/O can be affected by:

- Host device saturation
- Control-group limits
- Overlay filesystems
- Network namespaces
- Virtual Ethernet devices
- Shared interrupt processing

Containers do not remove host-level I/O constraints.

## 37. Cloud I/O Architecture

Cloud instances expose virtualized devices and service limits.

Performance can be constrained by:

- Instance network bandwidth
- Storage bandwidth
- Packet-per-second limits
- Volume limits
- Virtual NIC queues
- Host contention
- Burstable credits

The service attached to the instance and the instance type must be evaluated together.

## 38. Enhanced Networking

Cloud platforms provide accelerated network paths using paravirtualization or SR-IOV-like mechanisms.

Benefits may include:

- Higher packet rate
- Lower latency
- Reduced CPU overhead

The operating system must use compatible drivers and instance capabilities.

## 39. Common I/O Bottlenecks

- PCIe lane or generation limit
- Shared upstream link saturation
- Device queue saturation
- Interrupt concentration on one CPU
- Excessive interrupts
- Excessive polling
- Insufficient buffers
- Bufferbloat
- Memory bandwidth limit
- Virtualization overhead
- Driver or firmware defects
- Cloud service limits

## 40. Symptoms of Interrupt Saturation

- High system CPU time
- One or several CPUs unusually busy
- Packet loss or storage latency
- High interrupt rate
- Application CPU lower than total CPU
- Increased soft-interrupt processing

## 41. Symptoms of Bus or Link Saturation

- Device performance below specification
- Multiple devices slow simultaneously
- Throughput plateau despite more concurrency
- High queue depth
- No improvement after device upgrade

## 42. Troubleshooting Method

1. Confirm the user-visible impact.
2. Identify the I/O path and device.
3. Measure latency, throughput, queue depth, and error rate.
4. Inspect system CPU, interrupts, and per-core distribution.
5. Check driver, firmware, and negotiated link capability.
6. Check NUMA locality and device topology.
7. Check virtualization and cloud limits.
8. Inspect buffering, batching, and backpressure.
9. Reproduce with a representative workload.
10. Validate remediation across the full path.

## 43. Example — Fast NVMe, Slow Application

A fast NVMe device may not improve application performance when:

- The application is synchronous and single-threaded.
- The filesystem or database serializes writes.
- The PCIe link is constrained.
- The instance has a storage-bandwidth cap.
- The workload is CPU-bound.
- Queue depth is too low.
- Durability flushes dominate latency.

## 44. Example — High Network Throughput, High CPU

High packet processing can consume CPU because of:

- Interrupt handling
- Protocol processing
- Encryption
- Small packets
- Disabled offload
- Poor receive-queue distribution

Scaling network bandwidth may require CPU and queue tuning, not only a faster adapter.

## 45. Reliability Considerations

I/O architecture should handle:

- Device errors
- Timeouts
- Retries
- Partial completion
- Queue overflow
- Hot removal
- Driver recovery

Retries must be bounded and observable because uncontrolled retries can amplify overload.

## 46. Security Considerations

- DMA must be isolated.
- Drivers and firmware require patching.
- Passthrough reduces abstraction boundaries.
- Device access should follow least privilege.
- Diagnostic interfaces can expose sensitive data.
- Shared devices can create side-channel risk.

## 47. Common Misconceptions

### Misconception 1: A faster device always produces a faster application

The limiting factor may be the interface, software path, instance limit, or workload pattern.

### Misconception 2: Interrupts are always better than polling

Polling can be appropriate for extremely high-rate, low-latency workloads.

### Misconception 3: DMA eliminates CPU involvement

The CPU still configures operations, manages queues, handles completion, and processes data.

### Misconception 4: Containers isolate hardware performance

They share host devices and lower-level resource constraints.

### Misconception 5: High queue depth always improves throughput

Excessive queueing increases latency and may indicate saturation.

## 48. Architect's Mental Model

For any I/O path, ask:

1. Which device performs the work?
2. Which interconnect carries the data?
3. What is the negotiated link capacity?
4. How are requests queued?
5. How is completion signaled?
6. Is DMA used?
7. Where are buffers located?
8. What provides backpressure?
9. Which components are shared?
10. Which hardware, virtualization, or cloud limits apply?

## 49. Chapter Summary

- I/O architecture coordinates processors, memory, controllers, and peripheral devices.
- Modern systems use switched interconnects such as PCIe rather than one shared bus.
- PCIe performance depends on generation, lane count, and topology.
- Drivers and firmware connect operating-system abstractions to device behavior.
- Polling, interrupts, and DMA represent different coordination models.
- DMA reduces copying overhead but requires memory isolation through mechanisms such as IOMMU.
- Queues, batching, buffering, and backpressure determine throughput and latency.
- Device offload can improve performance while complicating observability.
- NUMA, virtualization, containers, and cloud limits influence the full I/O path.
- Troubleshooting must evaluate device, link, driver, interrupt, queue, memory, and platform constraints together.
