# Module 01 — Computing Foundations

# Chapter 01.07 — Storage Architecture and Persistent Storage Fundamentals

## 1. Purpose of This Chapter

Memory provides a fast working area for active applications, but its contents are volatile. Production systems require persistent storage to retain operating systems, application data, databases, logs, artifacts, backups, images, and business records across restarts and failures.

Storage architecture is often misunderstood as a capacity decision. In reality, architects must evaluate persistence, latency, throughput, IOPS, access pattern, concurrency, consistency, durability, availability, recoverability, security, and cost.

This chapter establishes the mental model required to reason about local disks, network storage, cloud volumes, shared filesystems, object stores, database storage, and container persistence.

## 2. Learning Objectives

After completing this chapter, you should be able to:

- Explain why persistent storage is required.
- Compare HDD, SSD, and NVMe media conceptually.
- Distinguish block, file, and object storage.
- Explain sectors, blocks, partitions, volumes, and filesystems.
- Interpret latency, throughput, IOPS, queue depth, and access patterns.
- Explain RAID, replication, snapshots, backups, and archives.
- Understand storage behavior in virtual machines, containers, Kubernetes, and AWS.
- Diagnose common storage bottlenecks and failure modes.

## 3. Persistence

Persistent storage retains data beyond the lifetime of a process, operating-system session, container, or power cycle.

Typical persistent data includes:

- Operating-system files
- Application binaries
- Databases
- User uploads
- Logs
- Build artifacts
- Container images
- Backups
- Audit records
- Configuration state

Persistence is not the same as durability. A device may retain data across restart but still fail permanently.

## 4. Storage Media

### 4.1 Hard Disk Drives

Hard disk drives store data magnetically on rotating platters.

Characteristics:

- Mechanical movement
- Higher access latency
- Good sequential throughput
- Lower cost per unit of capacity
- Sensitivity to seek patterns

### 4.2 Solid-State Drives

Solid-state drives store data in flash memory.

Characteristics:

- No moving parts
- Lower latency than HDDs
- Better random access
- Finite write endurance
- Internal garbage collection and wear leveling

### 4.3 NVMe

NVMe is a protocol and interface designed for modern nonvolatile memory over PCI Express.

Characteristics:

- High parallelism
- Low protocol overhead
- Multiple queues
- High IOPS and throughput

NVMe does not describe the persistence model by itself; it describes how the host communicates with the device.

## 5. Storage Stack

A simplified storage path may include:

1. Application
2. Runtime or database engine
3. Filesystem
4. Operating-system page cache
5. Block layer
6. Device driver
7. Virtualization or network layer
8. Storage device or distributed storage service

![Figure 01.07.01 — End-to-End Storage Stack](assets/01.07-fig-01-storage-stack.png)

A delay at any layer can affect application latency.

## 6. Sectors, Blocks, and Pages

### Sector

A low-level unit used by storage devices.

### Block

A logical unit used by operating systems and filesystems for I/O and allocation.

### Page

A memory-management unit. Database engines and flash devices may also use the word page for their own internal units.

Architects must identify the context because the same term can describe different layers.

## 7. Partitions and Volumes

### Partition

A defined region of a physical or virtual block device.

### Volume

A logical storage unit presented to the operating system or application.

A volume may be backed by:

- One disk
- A partition
- Several disks
- A RAID set
- A logical volume manager
- A cloud block service
- A distributed storage system

## 8. Filesystems

A filesystem organizes files and directories on block storage.

Responsibilities include:

- Naming
- Directory hierarchy
- Metadata
- Allocation
- Permissions
- Timestamps
- Free-space tracking
- Crash recovery

Examples include:

- NTFS
- ext4
- XFS
- APFS

Filesystem choice affects features, compatibility, performance, and recovery behavior.

## 9. Journaling

A journaling filesystem records intended metadata or data changes before final application.

This can improve recovery after interruption, but it does not replace backups or application-level consistency.

## 10. Mounting

A filesystem is attached to an operating-system directory hierarchy through a mount operation.

Mount configuration influences:

- Read/write behavior
- Execution permissions
- Access-time updates
- Performance
- Recovery behavior

## 11. Block Storage

Block storage exposes addressable blocks to a host.

The host normally creates partitions and filesystems or allows an application such as a database to manage blocks directly.

Suitable for:

- Boot volumes
- Databases
- General-purpose VM storage
- Low-latency application data

AWS example:

- Amazon EBS

## 12. File Storage

File storage exposes files and directories through a shared filesystem interface.

Suitable for:

- Shared application content
- Home directories
- Content management
- Legacy applications requiring POSIX-like files

AWS examples:

- Amazon EFS
- Amazon FSx

## 13. Object Storage

Object storage stores data as objects containing:

- Object data
- Metadata
- Identifier or key

It does not normally provide a traditional mounted block or filesystem interface.

Suitable for:

- Images
- Backups
- Logs
- Data lakes
- Static assets
- Artifacts

AWS example:

- Amazon S3

## 14. Block vs File vs Object

| Characteristic | Block | File | Object |
|---|---|---|---|
| Access model | Addressable blocks | Files and directories | API-based objects |
| Typical consumer | OS or database | Multiple clients or applications | Applications and services |
| Metadata | Limited at block layer | Filesystem metadata | Rich object metadata |
| Sharing | Usually attached to limited hosts | Designed for shared access | Designed for distributed access |
| Typical use | VM disks, databases | Shared files | Backups, media, data lakes |

## 15. Ephemeral Storage

Ephemeral storage is tied to the lifecycle of a host, instance, container, or temporary environment.

It may provide excellent performance but should not hold irreplaceable data unless replication or recovery is designed explicitly.

Examples include:

- Local temporary directories
- Instance-local disks
- Container writable layers
- Build-runner workspaces

## 16. Storage Performance Dimensions

### Latency

Time required to complete one operation.

### IOPS

Input/output operations per second.

### Throughput

Amount of data transferred per unit time.

### Queue Depth

Number of outstanding I/O operations waiting or executing.

### Concurrency

Number of clients, threads, or requests issuing I/O simultaneously.

These metrics must be interpreted together.

## 17. IOPS and Block Size

Approximate throughput relationship:

```text
Throughput = IOPS × I/O size
```

Example:

```text
10,000 IOPS × 4 KiB ≈ 39 MiB/s
```

The same IOPS with larger operations produces more throughput but may have different latency and device behavior.

## 18. Sequential and Random I/O

### Sequential I/O

Operations access adjacent locations.

Useful for:

- Streaming
- Large scans
- Backups
- Log writing

### Random I/O

Operations access nonadjacent locations.

Common in:

- Databases
- Metadata-heavy workloads
- Many-user filesystems

HDDs are especially sensitive to random I/O because mechanical seeks are required.

## 19. Read and Write Patterns

Architects should identify:

- Read-heavy or write-heavy
- Sequential or random
- Small or large I/O
- Synchronous or asynchronous
- Burst or sustained
- Single-client or concurrent

A storage service suitable for one pattern may perform poorly for another.

## 20. Synchronous Writes

A synchronous write requires confirmation that data has reached an agreed durability boundary before the application continues.

This improves correctness but can increase latency.

Databases use mechanisms such as write-ahead logging to balance correctness and performance.

## 21. Buffering and Caching

Writes may pass through application, operating-system, controller, and device buffers.

Reads may be served from cache rather than the underlying device.

Benchmark results can be misleading when caches are not considered.

## 22. Flush and Durability Semantics

A write being accepted does not always mean it is durably stored.

Applications requiring strong guarantees must understand:

- Flush behavior
- Filesystem semantics
- Device cache behavior
- Replication acknowledgment
- Database commit semantics

## 23. Queue Depth

Higher queue depth may improve throughput by allowing a device to reorder or parallelize work.

Excessive queue depth can increase latency and indicate saturation.

Averages may hide tail latency, which is often more important to user-facing systems.

## 24. RAID

RAID combines multiple disks for performance, capacity, or redundancy.

### RAID 0

Striping without redundancy.

### RAID 1

Mirroring.

### RAID 5

Striping with single parity.

### RAID 6

Striping with dual parity.

### RAID 10

Striping across mirrored pairs.

RAID is not a backup.

## 25. Replication

Replication stores copies of data on multiple devices, nodes, zones, or regions.

Replication can improve:

- Availability
- Durability
- Read scale
- Disaster recovery

It can also replicate accidental deletion, corruption, or malicious change.

## 26. Snapshots

A snapshot captures a point-in-time representation of storage state.

Snapshots may be:

- Full
- Incremental
- Crash-consistent
- Application-consistent

Snapshot creation is not automatically equivalent to a tested backup.

## 27. Backups

A backup is a recoverable copy maintained independently enough to support restoration after loss, corruption, or disaster.

A sound backup strategy defines:

- Scope
- Frequency
- Retention
- Encryption
- Immutability
- Recovery point objective
- Recovery time objective
- Restore testing

## 28. Archive Storage

Archive storage prioritizes cost and retention over immediate access.

Suitable for:

- Compliance records
- Long-term backups
- Historical datasets

Retrieval time and cost must be understood before selection.

## 29. Durability and Availability

### Durability

Probability that stored data remains intact over time.

### Availability

Probability that data can be accessed when required.

A system can be durable but temporarily unavailable, or available while holding corrupted data.

## 30. Consistency

Storage consistency describes when and how updates become visible to readers.

Architects should understand:

- Read-after-write behavior
- Concurrent updates
- Cache invalidation
- Replication lag
- Application conflict handling

## 31. Data Integrity

Data-integrity mechanisms include:

- Checksums
- Journaling
- Transaction logs
- Replication verification
- Scrubbing
- Versioning

Integrity must be monitored rather than assumed.

## 32. Encryption

Storage security typically includes:

- Encryption at rest
- Encryption in transit
- Key management
- Access control
- Audit logging
- Secure deletion

Encryption does not replace authorization or backup.

## 33. Secure Deletion

Deletion semantics vary by storage technology.

Flash devices, snapshots, replicas, and object versions may retain data after a logical delete.

Architects should define retention and destruction requirements explicitly.

## 34. Storage in Virtual Machines

A virtual machine may use:

- Virtual block volumes
- Local ephemeral disks
- Network filesystems
- Object storage through APIs

Performance may depend on both instance and volume limits.

## 35. Storage in Containers

A container's writable layer is usually ephemeral.

Persistent data should use an external volume or service.

Container image layers are optimized for packaging, not for general persistent application state.

## 36. Kubernetes Storage

Kubernetes provides abstractions including:

- Volume
- PersistentVolume
- PersistentVolumeClaim
- StorageClass
- Container Storage Interface driver

These abstractions separate workload requests from underlying storage implementation.

## 37. Access Modes

Persistent storage may support patterns such as:

- ReadWriteOnce
- ReadOnlyMany
- ReadWriteMany
- ReadWriteOncePod

Support depends on the storage backend and driver.

## 38. Stateful Workloads

Stateful workloads require careful design for:

- Identity
- Persistent volumes
- Ordering
- Replication
- Backup
- Recovery
- Rescheduling

A persistent volume alone does not make an application highly available.

## 39. AWS Storage Mapping

| Requirement | Common AWS service |
|---|---|
| VM block volume | Amazon EBS |
| Shared Linux file storage | Amazon EFS |
| Managed Windows or specialized filesystem | Amazon FSx |
| Object storage | Amazon S3 |
| Local high-performance ephemeral storage | EC2 instance store |
| Archive | S3 archival storage classes |

Service selection must follow workload requirements rather than familiarity.

## 40. EBS Considerations

When evaluating block volumes, consider:

- Volume type
- Provisioned IOPS
- Provisioned throughput
- Capacity
- Instance bandwidth limits
- Snapshot strategy
- Availability-zone attachment model

Increasing volume performance may not help if the instance itself is the bottleneck.

## 41. S3 Considerations

Object storage is accessed through APIs and is not a drop-in replacement for every filesystem workload.

Consider:

- Object key design
- Request pattern
- Versioning
- Lifecycle policy
- Encryption
- Access policy
- Replication
- Retrieval cost

## 42. Database Storage

Database performance depends on:

- Data-file access
- Transaction logs
- Buffer cache
- Checkpoints
- Temporary files
- Write amplification
- Synchronization guarantees

Database storage should be evaluated with representative workloads, not generic file-copy tests alone.

## 43. Storage Saturation Symptoms

Common symptoms include:

- Rising latency
- Growing queue depth
- Low application throughput
- High I/O wait
- Database timeouts
- Slow builds
- Delayed log writes
- Container startup delays

CPU utilization may remain low while storage is the bottleneck.

## 44. Capacity Exhaustion

When storage fills, systems may experience:

- Failed writes
- Database outage
- Logging failure
- Package-installation failure
- Node instability
- Corrupted temporary workflows

Capacity monitoring must include growth rate, not only current percentage.

## 45. Inodes and Metadata Exhaustion

A filesystem may run out of metadata structures such as inodes even when free byte capacity remains.

Large numbers of small files can create this condition.

## 46. Write Amplification

Write amplification occurs when the underlying system writes more data than the application logically requested.

Sources include:

- Flash translation layers
- RAID parity
- Filesystem journaling
- Database compaction
- Copy-on-write snapshots

## 47. Snapshot and Copy-on-Write Effects

Snapshots may increase storage usage and write overhead because changed blocks must be preserved.

Snapshot chains should be monitored and governed.

## 48. Storage Troubleshooting Method

1. Confirm user-visible impact.
2. Identify the affected layer.
3. Measure latency, IOPS, throughput, and queue depth.
4. Determine read/write and random/sequential patterns.
5. Check instance, volume, network, and service limits.
6. Inspect filesystem capacity and metadata.
7. Correlate with backups, snapshots, compaction, and deployments.
8. Verify data integrity and error logs.
9. Test with representative workload.
10. Validate remediation and recovery.

## 49. Benchmarking Principles

Storage benchmarks must specify:

- I/O size
- Read/write ratio
- Random/sequential pattern
- Queue depth
- Concurrency
- Dataset size
- Cache state
- Test duration
- Sync behavior

A benchmark without these details is difficult to interpret.

## 50. Common Misconceptions

### Misconception 1: More capacity means more performance

Capacity and performance may be independent or only partially related.

### Misconception 2: RAID is a backup

RAID improves availability against selected device failures but does not protect against deletion, corruption, or disaster.

### Misconception 3: A snapshot is automatically a complete backup

Snapshots require retention, independence, consistency, and restore validation.

### Misconception 4: Object storage is simply a remote filesystem

Its API, semantics, performance, and access patterns differ.

### Misconception 5: Low CPU means the system has spare capacity

The system may be blocked on storage latency.

## 51. Architect's Mental Model

For any storage requirement, ask:

1. What data must persist?
2. What access model is required?
3. What are the read and write patterns?
4. What latency, IOPS, and throughput are required?
5. How many clients access the data?
6. What durability and availability are required?
7. What consistency behavior is required?
8. How will backup and restore work?
9. How will encryption and access control work?
10. What are the capacity-growth and cost models?

## 52. Chapter Summary

- Persistent storage retains data beyond process and power cycles.
- HDD, SSD, and NVMe differ in latency, parallelism, endurance, and cost.
- Block, file, and object storage expose different access models.
- Storage performance must be understood through latency, IOPS, throughput, queue depth, and access pattern.
- Filesystems add naming, allocation, metadata, permissions, and recovery semantics.
- RAID, replication, snapshots, backups, and archives solve different problems.
- Durability, availability, consistency, and integrity are distinct properties.
- Containers require external persistence for durable state.
- Kubernetes storage abstractions do not remove application-level state responsibilities.
- AWS storage selection must follow workload access patterns and recovery requirements.
- Storage troubleshooting requires cross-layer evidence and representative workload analysis.
