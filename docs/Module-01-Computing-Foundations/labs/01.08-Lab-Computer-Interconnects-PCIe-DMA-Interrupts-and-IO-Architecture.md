# Lab 01.08 — Computer Interconnects, PCIe, DMA, Interrupts, and I/O Architecture

## 1. Lab Objective

This lab connects I/O architecture concepts to a real computer. You will inspect buses, PCIe devices, controllers, drivers, interrupt activity, queues, and device topology. You will then analyze how storage and network traffic move between devices, memory, the processor, and the operating system.

## 2. Expected Outcomes

After completing this lab, you should be able to:

- Identify PCIe and other peripheral devices.
- Map devices to drivers and controllers.
- Observe interrupt activity and per-core distribution.
- Explain DMA, buffering, queueing, batching, and backpressure.
- Identify possible link, queue, driver, or interrupt bottlenecks.
- Relate host I/O behavior to virtual machines, containers, Kubernetes, and AWS.
- Produce a structured I/O investigation report.

## 3. Safety

This lab is observational. Do not change firmware, disable devices, alter interrupt affinity, update drivers, or run destructive benchmarks on production or shared systems.

## 5. Part B — Inspect PCIe Topology

Where supported, identify:

- Root complex or host bridge
- PCIe switches or bridges
- Endpoints
- Link generation
- Link width

### Linux

```bash

```

Look for fields such as:

- `LnkCap`
- `LnkSta`
- `Width x1`, `x4`, `x8`, or `x16`

Answer:

2. Are multiple devices behind one bridge or upstream link?

4. Why can a newer device operate below its advertised maximum?

## 11. Part H — DMA Data-Flow Exercise

Draw or document two flows.

### Programmed I/O

```text
Device → CPU copies data → Memory
```

### DMA

```text
CPU configures transfer
Device ↔ Memory
Device interrupts CPU on completion
```

Explain:

1. Which work remains the processor's responsibility?
2. Which copying work is avoided?
3. Why is an IOMMU important?
4. What security risk exists if a device can access arbitrary memory?

## 13. Part J — Buffering and Backpressure

Analyze this pipeline:

```text
Application producer → memory buffer → network socket → NIC queue → network
```

The application produces 500 MiB/s, but the network can transmit only 200 MiB/s.

Answer:

1. Where will data accumulate?
2. What happens without bounded buffers?
3. What backpressure mechanism should be introduced?
4. How can large buffers increase latency?
5. Which metrics should be monitored?

## 18. Part O — AWS I/O Architecture Mapping

For each scenario, identify likely limiting layers.

### Scenario 1 — EC2 Network Plateau

An instance cannot exceed a fixed network throughput despite low application CPU.

### Scenario 2 — EBS Plateau

A volume is provisioned for more throughput, but the instance does not improve.

### Scenario 3 — High Packet Rate

Bandwidth is below the documented maximum, but packet processing saturates CPU.

### Scenario 4 — Accelerated Networking Disabled

A network-heavy workload shows higher CPU and lower packet performance than expected.

Consider:

- Instance bandwidth
- Packet-per-second limits
- Virtual NIC queues
- Enhanced networking
- EBS-optimized bandwidth
- Device and driver compatibility

## 19. Part P — I/O Incident Scenarios

For each scenario, identify likely causes, evidence, mitigation, and long-term remediation.

### Scenario 1

One CPU core is saturated with interrupts while other cores remain mostly idle.

### Scenario 2

A new NVMe device performs no faster than the previous device.

### Scenario 3

Network throughput is high, but latency increases sharply during bursts.

### Scenario 4

A VM performs well until several neighboring VMs begin intensive I/O.

### Scenario 5

A GPU is underutilized while host-to-device transfers dominate runtime.

### Scenario 6

A container application shows storage latency, while the host device itself appears healthy.
