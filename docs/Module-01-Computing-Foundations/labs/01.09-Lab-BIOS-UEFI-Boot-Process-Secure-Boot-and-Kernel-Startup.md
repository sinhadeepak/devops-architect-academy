# Lab 01.09 — BIOS, UEFI, Boot Process, Secure Boot, and Kernel Startup

## 1. Lab Objective

This lab connects boot architecture concepts to a running computer without making unsafe firmware or bootloader changes. You will identify the firmware mode, partition layout, EFI System Partition, boot entries, kernel version, boot parameters, early startup logs, service dependencies, Secure Boot state, and recovery options.

The goal is to learn how to determine the last successful boot stage and collect evidence before attempting repair.

## 2. Expected Outcomes

After completing this lab, you should be able to:

- Determine whether a system uses legacy BIOS or UEFI.
- Identify MBR or GPT partitioning.
- Locate the EFI System Partition where applicable.
- Inspect boot entries and bootloader configuration safely.
- Identify the running kernel and boot parameters.
- Inspect boot duration and failed services.
- Determine Secure Boot and TPM status where supported.
- Compare physical-machine, VM, cloud, container, and Kubernetes startup paths.
- Produce a structured boot investigation report.

## 3. Safety Rules

This lab is observational.

Do not:

- Change firmware settings.
- Change boot order.
- Disable Secure Boot.
- Rewrite partition tables.
- Reinstall or modify a bootloader.
- Delete EFI files.
- Modify kernel parameters.
- Reset or clear the TPM.
- Run recovery commands on production systems.

Record findings only.

## 4. Part A — Identify Firmware Mode

### Windows PowerShell

```powershell
Get-ComputerInfo | Select-Object BiosFirmwareType, BiosManufacturer, BiosVersion, BiosReleaseDate
```

Alternative:

```powershell
Confirm-SecureBootUEFI
```

The command may fail on legacy BIOS systems or systems without supported Secure Boot interfaces.

### Linux

```bash
if [ -d /sys/firmware/efi ]; then
  echo "UEFI mode"
else
  echo "Legacy BIOS mode"
fi
```

```bash
sudo dmidecode -t bios 2>/dev/null || true
```

### macOS

Modern Intel and Apple Silicon Macs use firmware-managed boot architectures rather than a legacy PC BIOS flow. Record the hardware model and boot environment:

```bash
system_profiler SPHardwareDataType
```

|---|---|
| Firmware mode | |
| Firmware vendor | |

| Firmware date | |
| Secure Boot support visible | |

## 6. Part C — Identify the EFI System Partition

### Windows

Use:

```powershell
Get-Partition | Where-Object {$_.GptType -eq '{c12a7328-f81f-11d2-ba4b-00a0c93ec93b}'}
```

Do not mount or modify the partition unless working in a disposable lab environment.

### Linux

```bash
findmnt /boot/efi 2>/dev/null || true
```

```bash
lsblk -f
```

Where safely accessible:

```bash
find /boot/efi/EFI -maxdepth 2 -type f 2>/dev/null
```

### Questions

1. What filesystem is used by the ESP?
2. Which vendor or operating-system directories are present?
3. Which EFI executable is likely used for boot?
4. Why must the ESP be protected from unauthorized modification?

## 10. Part G — Inspect Initramfs and Early Drivers

### Linux

List initramfs images:

```bash
ls -lh /boot/init* 2>/dev/null
```

Inspect contents using the tool available on your distribution:

```bash
lsinitramfs /boot/initrd.img-$(uname -r) 2>/dev/null | head -100
```

or:

```bash
lsinitrd 2>/dev/null | head -100
```

Identify whether the initramfs contains support for:

- Root filesystem
- Storage controller
- LVM
- RAID
- Disk encryption
- Network boot where relevant

Answer:

1. Why are some drivers required before the real root filesystem is mounted?
2. How can a kernel update succeed but the next boot fail because of initramfs?
3. Why must image pipelines include reboot validation?

## 11. Part H — Inspect Boot Logs

### Linux

Current boot:

```bash
journalctl -b --no-pager | head -200
```

Kernel messages:

```bash
journalctl -k -b --no-pager | head -200
```

Previous boot, where available:

```bash
journalctl -b -1 --no-pager | tail -200
```

### Windows

Query recent boot-related system events:

```powershell
Get-WinEvent -LogName System -MaxEvents 200 |
  Where-Object {$_.ProviderName -match 'Kernel|Boot|Service Control Manager'} |
  Select-Object TimeCreated, ProviderName, Id, LevelDisplayName, Message
```

### macOS

```bash
log show --last boot --style compact | head -200
```

Classify messages into:

- Firmware or boot manager
- Kernel
- Driver
- Filesystem
- Service startup
- Network startup
- Security

## 19. Part P — Boot Failure Scenarios

For each scenario, identify the most likely failed stage, required evidence, safe recovery path, and prevention.

### Scenario 1

The system powers on but shows only a hardware diagnostic LED code.

### Scenario 2

Firmware reports `No bootable device`.

### Scenario 3

Secure Boot rejects a newly installed boot component.

### Scenario 4

The bootloader menu appears, but the selected kernel cannot be found.

### Scenario 5

The kernel starts but reports that the root filesystem is unavailable.

### Scenario 6

The operating system enters emergency mode because a required mount fails.

### Scenario 7

A cloud VM boots, but cloud-init repeatedly fails and the instance never becomes application-ready.

### Scenario 8

A Kubernetes node completes OS boot but remains `NotReady`.
