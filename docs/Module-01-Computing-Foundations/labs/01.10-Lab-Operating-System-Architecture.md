# Lab 01.10 — Operating System Architecture

## 1. Lab Objective

This lab connects operating-system architecture to observable process, thread, kernel, scheduling, file-descriptor, signal, service, and resource-limit behavior. You will inspect a running system, create controlled processes, observe blocking and CPU-bound states, trace system calls where available, and analyze how the same mechanisms appear in containers and Kubernetes.

## 2. Expected Outcomes

After completing this lab, you should be able to:

- Distinguish kernel-space and user-space activity.
- Inspect processes, threads, process trees, and process states.
- Observe CPU-bound, blocked, sleeping, and terminated behavior.
- Explain system calls, signals, file descriptors, pipes, and sockets.
- Identify context switching, resource limits, and descriptor exhaustion risks.
- Explain PID 1, graceful termination, zombies, and process supervision.
- Relate namespaces and cgroups to containers.
- Produce a structured operating-system investigation report.

## 3. Safety

Use only temporary files and test processes. Do not change kernel parameters, service policies, production limits, security settings, or container-runtime configuration on shared systems.

## 6. Create and Observe a Child Process

Create `parent_child.py`:

```python
import os
import subprocess
import sys
import time

print(f"parent_pid={os.getpid()}")
child = subprocess.Popen([
    sys.executable,
    "-c",
    "import os,time; print(f'child_pid={os.getpid()} parent={os.getppid()}'); time.sleep(30)",
])
print(f"spawned_child={child.pid}")
time.sleep(30)
child.wait()
print(f"child_exit_code={child.returncode}")
```

Inspect the relationship while both processes are alive. Explain resource inheritance, exit-code collection, orphan behavior, and why process trees matter for service supervisors and container entrypoints.

## 8. Compare CPU-Bound and Sleeping Processes

Create a CPU-bound process and a sleeping process, run both for 30 seconds, and compare CPU usage, process state, scheduler demand, likely bottleneck, and benefit from additional CPU.

```python
# cpu_bound.py
import math, os, time
print(f"pid={os.getpid()}")
end = time.time() + 30
count = 0
while time.time() < end:
    for value in range(2, 10000):
        limit = int(math.sqrt(value)) + 1
        if all(value % divisor for divisor in range(2, limit)):
            count += 1
print(count)
```

```python

```

## 12. Signals and Graceful Shutdown

Create `graceful_service.py`:

```python
import os
import signal
import time

running = True

def stop(signum, frame):
    global running
    print(f"received_signal={signum}; beginning graceful shutdown")
    running = False

signal.signal(signal.SIGTERM, stop)
signal.signal(signal.SIGINT, stop)
print(f"pid={os.getpid()}")

while running:
    print("service running")
    time.sleep(2)

print("flushing state and exiting")
time.sleep(2)
```

Send a controlled termination signal. Explain cleanup, in-flight requests, grace periods, and Kubernetes termination behavior.

## 15. Zombie Processes

On a disposable Unix-like system, run:

```python
import os
import time

pid = os.fork()
if pid == 0:
    os._exit(0)

print(f"parent={os.getpid()} child={pid}")
time.sleep(30)
os.waitpid(pid, 0)
print("child reaped")
```

Explain why the child becomes a zombie, how it is reaped, and why PID 1 or a subreaper matters inside containers.

## 17. Incident Scenarios

For each scenario, identify likely causes, evidence, immediate mitigation, and long-term remediation:

1. High load, low CPU, and tasks in uninterruptible sleep.
2. High system CPU with low application user CPU.
3. `Too many open files` while accepting connections.
4. Continuous supervisor restart loop.
5. Container ignores `SIGTERM` and is force-killed.
6. Thousands of threads, high context switching, low throughput.
7. Process blocked indefinitely on a lock.
8. Host exhausts process identifiers or process slots.
