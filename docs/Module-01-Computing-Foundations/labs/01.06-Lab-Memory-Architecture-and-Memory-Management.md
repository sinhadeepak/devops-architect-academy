# Lab 01.06 — Memory Architecture and Memory Management

## 1. Lab Objective

This lab connects memory architecture concepts to observable system behavior. You will inspect physical and virtual memory, process working sets, swap or page-file configuration, page faults, cache usage, allocation growth, and container memory controls.

The goal is to distinguish healthy memory use from memory pressure, leaks, oversized caches, and incorrect limits.

## 2. Expected Outcomes

After completing this lab, you should be able to:

- Identify total, free, available, cached, and committed memory.
- Distinguish virtual size from resident memory.
- Observe process memory growth over time.
- Explain page faults and swap activity.
- Compare bounded allocation with unbounded growth.
- Interpret Kubernetes memory requests, limits, and `OOMKilled` behavior.
- Produce a structured memory investigation report.

## 3. Safety

Do not intentionally exhaust memory on production systems, shared servers, or corporate-managed machines. Use small, controlled test allocations and stop the exercise immediately if the system becomes unstable.

## 7. Part D — Observe a Controlled Allocation

Create `bounded_memory.py`:

```python
import os
import time

blocks = []

for step in range(10):
    blocks.append(bytearray(10 * 1024 * 1024))
    print(f"PID={os.getpid()} allocated={(step + 1) * 10} MiB")
    time.sleep(3)

print("Holding memory for 20 seconds")
time.sleep(20)
```

Run it and observe:

- Resident memory
- Virtual memory
- Available system memory
- Page faults where visible
- Whether memory returns after the process exits

Do not increase the allocation size unless the system has sufficient capacity.

## 8. Part E — Bounded Cache vs Leak-Like Growth

Create `bounded_cache.py`:

```python
from collections import deque
import os
import time

cache = deque(maxlen=20)

for step in range(100):
    cache.append(bytearray(2 * 1024 * 1024))
    if step % 10 == 0:
        print(f"PID={os.getpid()} step={step} cache_entries={len(cache)}")
    time.sleep(0.2)

print("Holding for observation")
time.sleep(20)
```

Create `unbounded_growth.py`:

```python
import os
import time

items = []

for step in range(100):
    items.append(bytearray(2 * 1024 * 1024))
    if step % 10 == 0:
        print(f"PID={os.getpid()} step={step} entries={len(items)}")
    time.sleep(0.2)

print("Holding for observation")
time.sleep(20)
```

Compare the memory curves.

| Characteristic | Bounded cache | Unbounded growth |
|---|---|---|
| Growth pattern | | |
| Stabilizes | | |
| Retention policy | | |
| Failure risk | | |
| Likely remediation | | |

## 11. Part H — Observe Memory-Mapped Files

Create a temporary 20 MiB file.

### Linux or macOS

```bash
dd if=/dev/zero of=memory-map-test.bin bs=1M count=20
```

### Windows PowerShell

```powershell
$bytes = New-Object byte[] (20MB)
[System.IO.File]::WriteAllBytes('memory-map-test.bin', $bytes)
```

Create `map_file.py`:

```python
import mmap
import os
import time

with open("memory-map-test.bin", "r+b") as file:
    with mmap.mmap(file.fileno(), 0) as mapping:
        print(f"PID={os.getpid()} mapped={len(mapping)} bytes")
        print(mapping[0])
        time.sleep(30)
```

Observe virtual and resident memory. Explain why mapping a file does not necessarily make every byte resident immediately.

Delete the temporary file after the exercise.

## 12. Part I — Garbage Collection Observation

Create `gc_workload.py`:

```python
import gc
import time

for cycle in range(20):
    objects = [{"value": value, "payload": "x" * 1000} for value in range(20000)]
    del objects
    collected = gc.collect()
    print(f"cycle={cycle} collected={collected}")
    time.sleep(0.5)
```

Observe memory behavior and answer:

1. Does memory return to the operating system immediately after every collection?
2. Why can a runtime retain heap capacity for reuse?
3. Why does garbage collection not prevent all memory leaks?
4. How could collection pauses affect latency?

## 15. Part L — Memory Incident Scenarios

For each scenario, identify likely causes, required evidence, and remediation.

### Scenario 1

Resident memory grows continuously after each request burst and never stabilizes.

### Scenario 2

Memory usage rises to a fixed level and then remains stable while cache-hit rate improves.

### Scenario 3

A Java service has frequent long garbage-collection pauses but no OOM events.

### Scenario 4

A node has low free memory but high available memory and no swap activity.

### Scenario 5

A pod restarts with `OOMKilled`, but node memory remains healthy.

### Scenario 6

Several VMs slow down simultaneously when the virtualization host is under pressure.
