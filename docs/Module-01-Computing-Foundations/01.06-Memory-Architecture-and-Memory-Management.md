# Module 01 — Computing Foundations

# Chapter 01.06 — Memory Architecture and Memory Management

## 1. Purpose of This Chapter

Processors execute instructions, but those instructions and their working data must be available somewhere. Main memory provides the active workspace in which operating systems, applications, libraries, buffers, caches, and runtime state are held while a computer is operating.

Memory problems frequently appear as application crashes, latency spikes, container restarts, excessive garbage collection, swapping, node instability, or poor cloud cost efficiency. A DevOps Architect must understand not only how much memory a system has, but how memory is addressed, allocated, cached, reclaimed, limited, and exhausted.

## 2. Learning Objectives

After completing this chapter, you should be able to:

- Explain the purpose and characteristics of RAM.
- Describe the memory hierarchy.
- Distinguish physical memory from virtual memory.
- Explain pages, page tables, address translation, page faults, and swap.
- Describe process address spaces, stack, heap, code, and mapped regions.
- Explain fragmentation, memory leaks, caching, and garbage collection.
- Interpret memory utilization, available memory, committed memory, and working sets.
- Explain memory behavior in virtual machines, containers, and Kubernetes.
- Diagnose memory pressure systematically.

## 3. What Is Main Memory?

Main memory, commonly called RAM, stores instructions and data that active processes need with low latency.

RAM is:

- Faster than persistent storage
- Slower than processor registers and caches
- Volatile
- Randomly addressable
- Shared and managed by the operating system

When power is removed, ordinary RAM loses its contents.

## 4. Why Memory Is Necessary

A processor cannot efficiently execute every instruction directly from persistent storage. Storage is optimized for capacity and persistence, while RAM is optimized for low-latency access to active working data.

Memory holds:

- Operating-system code and data
- Application code
- Process stacks and heaps
- File-system cache
- Network buffers
- Shared libraries
- Database buffers
- Runtime metadata

## 5. Memory Hierarchy

A simplified hierarchy is:

1. Registers
2. L1 cache
3. L2 cache
4. L3 cache
5. Main memory
6. Local persistent storage
7. Remote storage

As capacity increases, access generally becomes slower and cheaper per unit.

## 6. Physical Memory

Physical memory is the actual RAM installed in or assigned to a system.

The operating system tracks which physical regions are:

- Used
- Free
- Cached
- Reserved
- Shared
- Reclaimable

Not all installed memory is necessarily available to applications because hardware, firmware, the kernel, and reserved regions consume some capacity.

## 7. Memory Addresses

Memory is organized into addressable locations.

A memory address identifies where data can be found.

Modern systems typically use byte-addressable memory, meaning each address refers to one byte.

A 64-bit architecture can represent a very large theoretical address range, although processors and operating systems usually implement a smaller practical address space.

## 8. Physical and Virtual Addresses

Applications normally use virtual addresses rather than physical addresses directly.

The operating system and processor memory-management hardware translate virtual addresses into physical locations.

This abstraction provides:

- Process isolation
- Flexible allocation
- Shared memory
- Memory protection
- Efficient use of physical RAM
- Support for memory-mapped files

## 9. Virtual Memory

Virtual memory gives each process the appearance of having its own private, contiguous address space.

The virtual address space can be larger than the currently available physical RAM, but that does not mean unlimited memory is available. Actual behavior depends on operating-system policy, committed memory, swap, and workload access patterns.

## 10. Pages

Virtual memory is commonly divided into fixed-size blocks called pages.

Physical memory is divided into corresponding page frames.

The operating system maps virtual pages to physical frames.

Common page sizes include 4 KiB, although larger pages may also be supported.

## 11. Page Tables

Page tables store mappings from virtual pages to physical frames.

The processor's memory-management unit uses these mappings during address translation.

Page-table entries may include:

- Physical frame number
- Read permission
- Write permission
- Execute permission
- Present or absent state
- Dirty state
- Accessed state

## 12. Translation Lookaside Buffer

The translation lookaside buffer, or TLB, caches recent virtual-to-physical address translations.

Without a TLB, page-table lookups would add substantial overhead to memory access.

A TLB miss requires additional translation work.

## 13. Page Faults

A page fault occurs when a process accesses a virtual page that cannot be used immediately under the current mapping.

### Minor Page Fault

The page is available in memory but requires mapping or bookkeeping.

### Major Page Fault

The page must be loaded from persistent storage or another slower source.

Major page faults are much more expensive.

## 14. Swap and Paging to Disk

Swap provides disk-backed capacity that the operating system can use when RAM is under pressure.

Advantages:

- Can prevent immediate process failure
- Provides room for infrequently used pages

Disadvantages:

- Far slower than RAM
- Can produce severe latency
- Can cause thrashing

Swap is not a substitute for sufficient physical memory.

## 15. Thrashing

Thrashing occurs when the system spends excessive time moving pages between RAM and storage instead of performing useful work.

Symptoms include:

- Very high storage activity
- Low useful throughput
- Long application pauses
- High page-fault rates
- Poor responsiveness

## 16. Process Address Space

A process address space commonly contains:

- Program code
- Read-only data
- Global and static data
- Heap
- Stack
- Shared libraries
- Memory-mapped files

## 17. The Stack

The stack commonly stores:

- Function call frames
- Return addresses
- Local variables
- Function parameters

Stack allocation is fast and structured, but stack capacity is limited.

Excessive recursion or very large local allocations can cause stack overflow.

## 18. The Heap

The heap stores dynamically allocated memory.

Applications request heap memory through language runtimes or system allocators.

Heap management is more flexible than stack allocation but can introduce:

- Fragmentation
- Allocation overhead
- Memory leaks
- Garbage-collection pressure

## 19. Memory Allocation

Applications request memory from runtime allocators, which obtain and manage larger regions from the operating system.

Allocation behavior depends on:

- Programming language
- Runtime
- Allocator
- Object lifetime
- Threading model
- Memory access pattern

## 20. Memory Deallocation

Memory must eventually be released or made reusable.

Two broad models exist:

### Manual Management

The application explicitly allocates and frees memory.

Risk:

- Leaks
- Double frees
- Use-after-free defects

### Automatic Management

A garbage collector identifies unreachable objects and reclaims memory.

Risk:

- Collection pauses
- Increased memory overhead
- Delayed reclamation

## 21. Memory Leaks

A memory leak occurs when memory is no longer useful but remains referenced or otherwise unreleased.

Symptoms may include:

- Gradually increasing resident memory
- Increasing garbage-collection activity
- Eventual out-of-memory failure
- Container restart
- Node pressure

Not every increase is a leak. Applications may intentionally retain caches or buffers.

## 22. Caching vs Leaking

A cache is retained for future reuse and should usually have a policy for size, expiration, or eviction.

A leak provides no intended future value and grows without effective control.

To distinguish them, examine:

- Growth pattern
- Eviction behavior
- Correlation with workload
- Object-retention profiles
- Recovery after idle periods
- Application configuration

## 23. Fragmentation

### Internal Fragmentation

Allocated blocks contain unused space.

### External Fragmentation

Free memory exists but is divided into regions that are unsuitable for a requested allocation.

Allocators and virtual memory reduce some fragmentation effects but do not eliminate them.

## 24. Shared Memory

Shared memory allows multiple processes to access the same physical memory region.

It can improve performance by avoiding data copying, but requires synchronization and access control.

## 25. Memory-Mapped Files

Memory mapping exposes file contents through a process's virtual address space.

Benefits include:

- Simplified access
- Operating-system caching
- Shared mappings
- Efficient large-file processing

## 26. File-System Cache

Operating systems use available RAM to cache file data.

This means high memory usage is not necessarily unhealthy. Cached memory may be reclaimed when applications need it.

The more meaningful question is often:

> How much memory is available for new demand without severe reclaim or swapping?

## 27. Free Memory and Available Memory

### Free Memory

Memory not currently used for anything.

### Available Memory

An estimate of memory that can be supplied to applications without significant swapping, including reclaimable cache.

A system may have little free memory but still have sufficient available memory.

## 28. Resident and Virtual Memory

### Virtual Size

The total virtual address space mapped or reserved by a process.

### Resident Set Size

The portion currently present in physical RAM.

A large virtual size does not necessarily mean the process is consuming the same amount of RAM.

## 29. Working Set

A working set is the set of memory pages a process actively uses over a period.

Performance is best when the working set fits in RAM and frequently accessed data remains cache-friendly.

## 30. Committed Memory

Committed memory represents memory the operating system has promised to processes, subject to system policy.

Commitment may be backed by:

- RAM
- Swap or page file
- Overcommit policy

Committed memory and currently resident memory are not the same.

## 31. Memory Pressure

Memory pressure occurs when demand approaches or exceeds the system's ability to supply usable memory efficiently.

Possible responses include:

- Cache reclamation
- Paging
- Swap activity
- Process termination
- Container eviction
- Allocation failure

## 32. Out-of-Memory Conditions

When the system cannot satisfy memory demand, it may:

- Fail an allocation
- Terminate a process
- Invoke an out-of-memory killer
- Restart a container
- Evict workloads
- Become unresponsive

The exact behavior depends on operating system and platform policy.

## 33. The Linux OOM Killer

Linux may terminate one or more processes when memory cannot be reclaimed sufficiently.

Selection depends on factors such as:

- Memory consumption
- Process importance adjustments
- System policy

An OOM kill is a symptom of memory pressure, not the root cause by itself.

## 34. Windows Memory Concepts

Windows commonly reports concepts such as:

- Working set
- Commit size
- Private bytes
- Standby cache
- Page file usage

These metrics describe different aspects of allocation and residency.

## 35. Garbage Collection

Garbage-collected runtimes manage memory automatically.

Common behaviors include:

- Heap growth
- Generational collection
- Pause events
- Compaction
- Concurrent collection

Poorly tuned heaps can create either excessive collection overhead or excessive memory consumption.

## 36. Stop-the-World Pauses

Some garbage-collection phases pause application execution.

Long pauses can appear as latency spikes even when average CPU and memory metrics look acceptable.

## 37. Memory in Virtual Machines

A virtual machine receives a configured quantity of virtual RAM.

The hypervisor maps guest memory to host physical memory.

Possible techniques include:

- Reservation
- Overcommit
- Ballooning
- Host swapping

Memory contention at the host layer can affect guests.

## 38. Memory Ballooning

Ballooning allows a hypervisor to reclaim memory from a guest through a special driver.

The guest operating system is encouraged to release or page memory.

This can reduce guest performance under host pressure.

## 39. Memory in Containers

Containers share host memory but can be constrained through control groups.

A container memory limit defines a hard boundary for memory usage under the platform's accounting model.

When the limit is exceeded, the container may be terminated.

## 40. Kubernetes Memory Requests and Limits

Example:

```yaml
resources:
  requests:
    memory: "512Mi"
  limits:
    memory: "1Gi"
```

### Request

Influences scheduling and represents expected minimum capacity.

### Limit

Defines the maximum allowed memory usage.

Unlike CPU, memory cannot simply be throttled when the limit is exceeded. The workload may be terminated.

## 41. OOMKilled Containers

A Kubernetes container may show an `OOMKilled` termination reason when it exceeds its memory limit or is selected under node memory pressure.

Investigation should include:

- Container limit
- Working-set growth
- Heap configuration
- Node pressure
- Recent traffic
- Caches
- Memory leaks
- Sidecar usage

## 42. Kubernetes Quality of Service

Kubernetes assigns quality-of-service classes based on requests and limits.

These classes influence behavior under resource pressure.

Architects should understand how resource declarations affect scheduling and eviction priority.

## 43. Memory Requests and Scheduling

An inaccurate memory request can cause:

- Poor bin packing
- Scheduling failures
- Node overcommit
- Unnecessary cost
- Increased eviction risk

Requests should reflect realistic sustained requirements with appropriate headroom.

## 44. Memory Is Not Compressible Like CPU

CPU demand can be delayed or throttled.

Memory demand requires capacity for retained state. When memory is unavailable, the platform cannot safely defer arbitrary memory use in the same way. It must reclaim, page, fail, or terminate.

## 45. Cloud Memory Sizing

Cloud instance selection should consider:

- Baseline working set
- Peak usage
- Growth behavior
- Cache requirements
- Heap configuration
- Operating-system overhead
- Sidecars and agents
- Failover capacity
- Cost

## 46. Memory-Optimized Instances

Memory-optimized instances provide a higher memory-to-vCPU ratio.

They are useful for workloads such as:

- In-memory databases
- Caches
- Large JVM heaps
- Analytics
- Memory-intensive data processing

## 47. NUMA

Non-uniform memory access architectures divide memory across nodes associated with processors or sockets.

Access to local memory is generally faster than access to remote memory.

NUMA becomes important in large systems, databases, and high-performance workloads.

## 48. Huge Pages

Huge pages use larger page sizes to reduce page-table and TLB overhead.

They may benefit certain workloads but can increase allocation complexity and wasted space.

## 49. Memory Bandwidth and Latency

Memory performance depends on more than capacity.

Important characteristics include:

- Access latency
- Bandwidth
- Channel configuration
- NUMA locality
- Cache effectiveness

A workload may be memory-bandwidth-bound even when sufficient capacity is available.

## 50. Common Memory Problems

- Memory leak
- Oversized cache
- Excessive heap
- Undersized heap
- Fragmentation
- Swap thrashing
- Container limit too low
- Request too low or too high
- Large page cache pressure
- Host overcommit
- Excessive sidecar consumption
- Unbounded queues or buffers

## 51. Troubleshooting Method

When investigating memory issues:

1. Confirm user-visible impact.
2. Identify whether the issue is capacity, residency, allocation, or latency related.
3. Inspect available memory, swap, and page faults.
4. Identify the largest consumers.
5. Compare virtual size, resident size, working set, and private memory.
6. Check growth over time.
7. Inspect container and node limits.
8. Review heap and garbage-collection behavior.
9. Correlate with traffic and recent deployments.
10. Verify the effect of remediation.

## 52. Capacity vs Leak Analysis

A stable application that consistently requires more memory than provisioned has a sizing problem.

An application whose memory grows without stabilizing may have:

- Leak
- Unbounded cache
- Queue backlog
- Workload accumulation

Time-series behavior is essential.

## 53. Common Misconceptions

### Misconception 1: Used memory is bad

Operating systems intentionally use free memory for caching.

### Misconception 2: Virtual memory equals RAM consumption

Virtual address space and resident physical memory differ.

### Misconception 3: Swap is equivalent to extra RAM

Swap is much slower and excessive use can cause severe performance degradation.

### Misconception 4: Increasing a container limit fixes memory leaks

It may only delay failure.

### Misconception 5: Garbage collection prevents leaks

Objects that remain referenced cannot be reclaimed.

## 54. Security Considerations

Memory safety and isolation affect security through:

- Buffer overflows
- Use-after-free defects
- Memory disclosure
- Privilege-boundary enforcement
- Secret retention in memory
- Core dumps
- Shared-memory access

Sensitive data should be minimized, protected, and removed from memory where feasible.

## 55. Architect's Mental Model

For a memory-dependent system, ask:

1. What is the steady-state working set?
2. What is peak usage?
3. Is growth bounded?
4. What memory is private, shared, cached, or reclaimable?
5. Is swap active?
6. Are page faults increasing?
7. Is garbage collection healthy?
8. Are container requests and limits realistic?
9. What happens when memory is exhausted?
10. Is scaling up, reducing retention, or redesigning the workload most appropriate?

## 56. Chapter Summary

- RAM provides low-latency volatile storage for active instructions and data.
- Virtual memory gives processes isolated address spaces.
- Pages, page tables, the MMU, and TLB implement address translation.
- Page faults and swap can introduce substantial latency.
- Process memory includes code, stack, heap, libraries, and mapped regions.
- Used memory may include healthy, reclaimable cache.
- Resident memory, virtual size, working set, and committed memory describe different concepts.
- Memory leaks, oversized caches, and fragmentation require different remedies.
- Containers can be terminated when memory limits are exceeded.
- Kubernetes requests affect scheduling; limits define a hard boundary.
- Memory troubleshooting requires time-series analysis, process-level evidence, and platform context.
