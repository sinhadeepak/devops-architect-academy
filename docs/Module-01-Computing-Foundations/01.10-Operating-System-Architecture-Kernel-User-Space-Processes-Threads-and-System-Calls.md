# Module 01 — Computing Foundations

# Chapter 01.10 — Operating System Architecture: Kernel, User Space, Processes, Threads, and System Calls

## 1. Purpose of This Chapter

An operating system is the control layer between applications and hardware. It schedules processor time, allocates memory, manages storage, exposes network interfaces, enforces security boundaries, handles devices, and provides standard abstractions such as files, processes, sockets, and virtual memory.

For a DevOps Architect, operating-system architecture is foundational. Containers share a host kernel. Virtual machines run complete guest operating systems. CI/CD agents execute as processes. Kubernetes nodes depend on kernel networking, filesystems, control groups, namespaces, and process supervision. Most production incidents eventually require reasoning about operating-system behavior.

## 2. Learning Objectives

After completing this chapter, you should be able to:

- Explain why operating systems exist.
- Describe the major responsibilities of a kernel.
- Differentiate kernel space and user space.
- Explain processes, threads, process states, and context switching.
- Describe system calls and privilege transitions.
- Explain scheduling, priorities, signals, exceptions, and interrupts.
- Describe files, descriptors, sockets, pipes, and inter-process communication.
- Relate operating-system mechanisms to containers, virtual machines, security, and troubleshooting.

## 3. What Is an Operating System?

An operating system is system software that manages hardware resources and provides controlled services to applications.

Its two broad goals are:

1. **Abstraction** — present usable interfaces instead of raw hardware details.
2. **Resource management** — allocate shared resources safely and efficiently.

Applications normally do not control processors, memory controllers, disks, or network adapters directly. They request services from the operating system.

## 4. Major Operating-System Responsibilities

An operating system commonly manages:

- Processor scheduling
- Processes and threads
- Virtual memory
- Filesystems and storage
- Device drivers
- Networking
- Identity and permissions
- Inter-process communication
- Time and timers
- Logging and auditing
- Service startup and shutdown
- Error handling and recovery

## 5. Kernel

The kernel is the privileged core of the operating system.

It performs operations that ordinary applications are not allowed to perform directly, including:

- Configuring memory mappings
- Scheduling threads
- Handling interrupts
- Managing devices
- Enforcing access control
- Creating processes
- Managing network stacks
- Mounting filesystems

A kernel defect can affect the entire system because the kernel operates with broad privilege.

## 6. Kernel Space and User Space

### Kernel Space

The privileged execution environment where the kernel and many drivers operate.

### User Space

The restricted environment where ordinary applications and services execute.

This separation limits the damage that one application can cause. A user-space process cannot normally access arbitrary physical memory or device registers.

## 7. Privilege Modes

Processors provide privilege levels or modes.

A simplified model is:

- Privileged mode for kernel execution
- Unprivileged mode for applications

The operating system uses processor privilege mechanisms to enforce isolation.

## 8. Monolithic and Microkernel Concepts

### Monolithic Kernel

Many core services and drivers execute in kernel space.

Advantages:

- Efficient communication
- High performance

Risks:

- Large privileged code base
- Driver defects can affect the whole system

### Microkernel

Keeps a smaller privileged kernel and moves more services to user space.

Advantages:

- Stronger isolation
- Smaller trusted core

Trade-offs:

- Additional communication overhead
- Greater architectural complexity

Modern operating systems often combine ideas from several designs.

## 9. System Calls

A system call is a controlled request from a user-space process to the kernel.

Examples include requests to:

- Open a file
- Read data
- Write data
- Create a process
- Allocate memory
- Create a socket
- Send network traffic
- Change permissions

System calls form the primary interface between applications and the kernel.

## 10. System Call Flow

A simplified flow is:

1. Application calls a library function.
2. The library prepares arguments.
3. A processor instruction transitions to kernel mode.
4. The kernel validates the request.
5. The kernel performs or schedules the operation.
6. A result or error is returned.
7. Execution returns to user mode.

## 11. Libraries and APIs

Applications often use high-level library functions rather than invoking system calls directly.

For example:

- A language runtime may expose file APIs.
- A standard library may wrap operating-system calls.
- A framework may hide sockets behind an HTTP client.

The abstraction remains dependent on operating-system services.

## 12. Processes

A process is an operating-system abstraction representing a running program and its associated resources.

A process commonly includes:

- Virtual address space
- One or more threads
- Open files and sockets
- Security identity
- Environment variables
- Current working directory
- Resource limits
- Process identifier

A program is a stored set of instructions. A process is an executing instance of a program.

## 13. Process Creation

Process creation typically involves:

- Creating process metadata
- Establishing an address space
- Inheriting or assigning resources
- Loading a program image
- Creating an initial thread
- Scheduling it for execution

On Unix-like systems, process creation often involves `fork` and `exec` concepts. Windows uses different APIs and internal mechanisms, but the architectural purpose is similar.

## 14. Parent and Child Processes

Processes may have parent-child relationships.

The parent may:

- Create the child
- Pass environment and handles
- Monitor completion
- Collect exit status
- Terminate or restart the child

Process trees help explain service supervision, shells, CI jobs, and container entrypoints.

## 15. Process Identifiers

Each process has an identifier, commonly called a PID.

PIDs are used for:

- Monitoring
- Signaling
- Debugging
- Resource accounting
- Process ownership

PIDs can be reused after a process exits, so long-term correlation should include timestamps or stronger identifiers.

## 16. Threads

A thread is a schedulable execution sequence within a process.

Threads within the same process usually share:

- Address space
- Code
- Heap
- Open file descriptors

Each thread has its own:

- Execution registers
- Stack
- Scheduling state
- Thread identifier

## 17. Process vs Thread

| Characteristic | Process | Thread |
|---|---|---|
| Address space | Separate | Shared within process |
| Isolation | Stronger | Weaker |
| Communication | IPC required | Shared memory directly |
| Creation cost | Usually higher | Usually lower |
| Failure impact | Often contained | May corrupt whole process |

## 18. Process States

A simplified process or thread state model includes:

- New
- Ready or runnable
- Running
- Waiting or blocked
- Stopped or suspended
- Terminated

A task may be alive but not consuming CPU because it is waiting for I/O, a lock, a timer, or another event.

## 19. Scheduler

The scheduler decides which runnable thread executes on which logical processor and for how long.

Scheduling goals may include:

- Fairness
- Responsiveness
- Throughput
- Priority handling
- Real-time guarantees
- Power efficiency

No scheduler can optimize every goal simultaneously.

## 20. Time Slices and Preemption

A time slice is a period during which a thread may run before the scheduler can choose another.

Preemption allows the operating system to interrupt a running thread and schedule another.

Preemption improves responsiveness but creates context-switch overhead.

## 21. Context Switching

A context switch changes execution from one thread or process to another.

The operating system must save and restore state such as:

- Registers
- Instruction pointer
- Stack pointer
- Scheduling metadata
- Memory context where required

Context switches also disrupt processor caches and translation state.

## 22. Scheduling Priorities

Operating systems may assign priorities to threads or processes.

Higher priority can improve responsiveness for selected work but may starve lower-priority tasks.

Priority should not be used to hide capacity or design problems.

## 23. CPU Affinity

CPU affinity restricts or prefers execution on selected processors.

Potential uses include:

- Reducing cache movement
- Aligning with NUMA locality
- Isolating latency-sensitive workloads

Risks include:

- Uneven load
- Reduced scheduler flexibility
- Single-core bottlenecks

## 24. Real-Time Scheduling

Real-time scheduling prioritizes predictable timing over general fairness.

It is used in specialized systems where deadlines matter.

Incorrect real-time configuration can make a system unresponsive by starving ordinary work.

## 25. Exceptions and Faults

An exception is a processor-detected event caused by instruction execution.

Examples include:

- Division by zero
- Invalid instruction
- Page fault
- Protection violation

The kernel handles the event and may resume, signal, or terminate the process.

## 26. Hardware Interrupts

Hardware interrupts originate from devices or timers.

They notify the processor that an event requires attention.

Interrupts differ from system calls because the device or hardware initiates them rather than the application.

## 27. Signals and Asynchronous Notifications

Unix-like systems use signals to notify processes of events.

Examples include:

- Termination request
- Interrupt from terminal
- Child-process exit
- Invalid memory access
- Timer expiration

Applications should handle termination signals cleanly where appropriate.

## 28. Graceful Termination

A graceful shutdown gives an application time to:

- Stop accepting work
- Complete or reject in-flight requests
- Flush data
- Close connections
- Release locks
- Record final state

Forced termination may be necessary when a process does not respond, but it increases data-integrity risk.

## 29. Exit Codes

Processes return exit codes to indicate success or failure.

By convention on Unix-like systems:

- `0` means success
- Nonzero means failure or a specific condition

Automation must interpret exit codes correctly rather than relying only on printed output.

## 30. File Descriptors and Handles

Operating systems represent open resources using identifiers.

Unix-like systems commonly use file descriptors for:

- Files
- Sockets
- Pipes
- Devices

Windows uses handles for similar resource references.

These identifiers are process-local references to kernel-managed objects.

## 31. Standard Streams

Processes commonly begin with standard streams:

- Standard input
- Standard output
- Standard error

Shell pipelines and container logging depend heavily on these streams.

Applications that write logs only to local files may be harder to operate in ephemeral environments.

## 32. Pipes

A pipe transfers data between processes.

Example:

```bash
producer | consumer
```

Pipes enable composition but introduce buffering, blocking, and backpressure behavior.

## 33. Sockets

A socket is an operating-system abstraction for communication.

Sockets can support:

- Local inter-process communication
- TCP
- UDP
- Unix-domain communication

Network applications depend on kernel socket buffers, routing, protocol handling, and device drivers.

## 34. Inter-Process Communication

IPC mechanisms include:

- Pipes
- Named pipes
- Sockets
- Shared memory
- Message queues
- Signals
- Semaphores
- Files

Each method trades simplicity, performance, reliability, and isolation.

## 35. Synchronization

Threads and processes coordinate access to shared state using mechanisms such as:

- Mutexes
- Semaphores
- Condition variables
- Read-write locks
- Atomic operations

Incorrect synchronization can create races, deadlocks, starvation, or priority inversion.

## 36. Race Conditions

A race condition occurs when the outcome depends on uncontrolled timing between concurrent operations.

Race conditions can produce intermittent failures that are difficult to reproduce.

## 37. Deadlocks

A deadlock occurs when tasks wait indefinitely for resources held by one another.

Common conditions include:

- Mutual exclusion
- Hold and wait
- No preemption
- Circular wait

Prevention requires disciplined lock ordering, timeouts, or redesign.

## 38. Starvation and Priority Inversion

### Starvation

A task receives insufficient access to a required resource.

### Priority Inversion

A high-priority task waits for a lower-priority task holding a resource.

These issues appear in schedulers, thread pools, queues, and lock-heavy applications.

## 39. Virtual Memory and Process Isolation

Each process normally receives its own virtual address space.

The kernel enforces access permissions such as:

- Read
- Write
- Execute

This limits accidental or malicious access between processes.

## 40. Copy-on-Write

Copy-on-write allows processes to share memory pages until one process modifies a page.

This improves process creation efficiency and supports snapshots and memory sharing.

## 41. Memory-Mapped Files

A file can be mapped into a process address space.

This allows file contents to be accessed through memory operations while the kernel manages paging and caching.

## 42. Filesystems and the Virtual File Interface

Operating systems often expose multiple filesystem types through a common interface.

Applications can use similar operations across:

- Local disk filesystems
- Network filesystems
- Pseudo-filesystems
- Device files

Abstraction simplifies software but filesystem semantics may still differ.

## 43. Device Drivers

Drivers allow the kernel to control hardware or virtual devices.

A driver may manage:

- Initialization
- Queues
- Interrupts
- DMA
- Error recovery
- Power management

Driver defects can cause performance degradation, crashes, or security vulnerabilities.

## 44. Kernel Modules

Some kernels support dynamically loaded modules.

Modules can add:

- Drivers
- Filesystems
- Network features
- Security mechanisms

Module loading should be governed because modules execute with kernel privilege.

## 45. Networking Stack

The operating system implements protocol processing such as:

- Ethernet handling
- IP routing
- TCP and UDP
- Firewalling
- Connection tracking
- Socket management

Application network behavior therefore depends on both process logic and kernel networking.

## 46. Identity and Permissions

The operating system associates processes with security identities.

Access decisions may use:

- User identity
- Group membership
- Capabilities or privileges
- File permissions
- Access-control lists
- Security policies

Least privilege reduces the impact of application compromise.

## 47. Privileged Operations

Operations such as binding certain ports, mounting filesystems, loading modules, changing network configuration, or accessing devices may require elevated privilege.

Applications should receive only the privileges they need.

## 48. Services and Daemons

A service or daemon is a long-running background process managed by the operating system or a supervisor.

A service manager may provide:

- Startup ordering
- Automatic restart
- Environment configuration
- Logging integration
- Dependency management
- Resource controls

## 49. Process Supervision

A supervisor monitors child processes and may restart them after failure.

Restarts improve availability but can hide repeated failure unless restart loops are monitored.

## 50. Resource Limits

Operating systems can restrict resources such as:

- CPU time
- Memory
- Open files
- Processes or threads
- Locked memory
- Core-dump size

Resource limits protect the system from uncontrolled consumption.

## 51. Control Groups

Linux control groups organize processes and account for or limit resources.

They can manage:

- CPU
- Memory
- I/O
- Process counts

Containers rely heavily on control groups for resource governance.

## 52. Namespaces

Linux namespaces provide isolated views of system resources.

Examples include:

- Process identifiers
- Mount points
- Network interfaces
- Hostname
- Users
- IPC resources

Namespaces create isolation but do not provide a separate kernel.

## 53. Containers and the Host Kernel

A container is a set of processes isolated and constrained by operating-system mechanisms.

Containers share the host kernel.

This means:

- Kernel vulnerabilities affect container security.
- Host kernel capabilities limit container behavior.
- Containers start faster than virtual machines.
- Different kernel families cannot normally run directly in the same host kernel.

## 54. Virtual Machines and Guest Kernels

A virtual machine runs a complete guest operating system and kernel on virtual hardware.

Compared with containers, VMs provide stronger kernel isolation but consume more resources and have longer startup times.

## 55. Process Model in Kubernetes

A Kubernetes pod contains one or more containers, and each container runs one or more processes.

Operational implications include:

- PID 1 behavior inside containers
- Signal forwarding
- Graceful termination
- Shared pod networking
- Shared volumes
- Resource accounting

## 56. PID 1 in Containers

The first process inside a container has special responsibilities.

If it does not handle signals or reap child processes correctly, the container may:

- Shut down uncleanly
- Accumulate zombie processes
- Ignore termination requests

Minimal init processes are sometimes used to address these issues.

## 57. Zombie Processes

A zombie is a terminated child process whose exit status has not yet been collected by its parent.

Zombies do not consume normal execution resources, but excessive accumulation indicates broken process supervision.

## 58. Orphan Processes

An orphan process continues after its parent exits.

The operating system reassigns it to a suitable supervisor, traditionally PID 1 or a subreaper.

## 59. System Calls and Performance

System calls introduce overhead because they require validation and privilege transition.

Applications improve efficiency through:

- Buffering
- Batching
- Asynchronous I/O
- Fewer copies
- Caching

Optimization must not weaken correctness or observability.

## 60. User CPU and System CPU

### User CPU Time

Time spent executing application instructions in user space.

### System CPU Time

Time spent executing kernel work on behalf of processes or handling system activity.

High system CPU may indicate:

- Heavy networking
- Storage operations
- Excessive system calls
- Interrupt load
- Lock contention in the kernel

## 61. Blocking and Nonblocking I/O

### Blocking I/O

The calling thread waits until the operation progresses or completes.

### Nonblocking I/O

The call returns when it cannot proceed immediately, allowing the application to do other work.

Event-driven systems use nonblocking I/O to serve many connections with fewer threads.

## 62. Asynchronous I/O

Asynchronous I/O allows an application to submit work and receive completion later.

This can improve concurrency but increases state-management complexity.

## 63. Thread Pools

A thread pool reuses a bounded set of worker threads.

Benefits include:

- Controlled concurrency
- Reduced thread-creation overhead
- Predictable resource use

Risks include:

- Queue buildup
- Starvation
- Deadlock
- Incorrect pool sizing

## 64. Event Loops

An event loop processes events and I/O readiness through one or a small number of threads.

It works well for I/O-heavy workloads but can be blocked by long CPU-bound tasks.

## 65. Common Operating-System Bottlenecks

- CPU scheduling contention
- Excessive context switching
- Lock contention
- Runaway process creation
- Open-file exhaustion
- Socket exhaustion
- Memory pressure
- I/O wait
- Interrupt saturation
- Kernel or driver defects
- Misconfigured resource limits

## 66. File Descriptor Exhaustion

A process or system can run out of file descriptors or handles.

Symptoms include failures to:

- Open files
- Accept connections
- Create pipes
- Start subprocesses

The root cause may be a leak, insufficient limits, or excessive concurrency.

## 67. Process Exhaustion

Unbounded process or thread creation can exhaust:

- PID space
- Memory
- Scheduler capacity
- Kernel objects

Fork bombs are an extreme example.

## 68. Core Dumps

A core dump records process memory and state after a crash.

It can support debugging but may contain:

- Secrets
- Personal data
- Cryptographic material

Core-dump handling requires security and retention controls.

## 69. Observability Sources

Operating-system investigation may use:

- Process listings
- Thread listings
- Scheduler metrics
- System-call tracing
- Kernel logs
- Audit logs
- Open-file inspection
- Network socket inspection
- Resource-limit inspection
- Crash dumps

The correct tool depends on the suspected layer.

## 70. Troubleshooting Method

1. Confirm user-visible impact.
2. Identify affected processes and services.
3. Inspect process state, CPU, memory, and I/O.
4. Determine whether tasks are running, runnable, blocked, or stopped.
5. Inspect threads, locks, and queues.
6. Check file descriptors, sockets, and resource limits.
7. Correlate user and system CPU.
8. Review kernel and service logs.
9. Compare with recent changes.
10. Validate remediation under representative load.

## 71. Example — High Load, Low CPU

A system can show high load with low CPU utilization when many tasks are blocked in uninterruptible I/O waits.

Evidence should include:

- Task states
- Storage latency
- I/O wait
- Queue depth
- Kernel logs

## 72. Example — High System CPU

High system CPU can result from:

- Packet processing
- Frequent system calls
- Context switching
- Filesystem activity
- Driver work
- Interrupt handling

Scaling application replicas may not solve a kernel-path bottleneck.

## 73. Example — Container Will Not Stop

A container may ignore graceful termination when:

- PID 1 does not handle the signal.
- A shell entrypoint fails to forward signals.
- The application is blocked.
- Shutdown takes longer than the grace period.

The platform may eventually force termination.

## 74. Security Considerations

Operating-system security depends on:

- Kernel patching
- Driver and module control
- Least privilege
- Process isolation
- Memory protection
- Secure service configuration
- Auditability
- Resource limits

A vulnerable kernel can undermine every process and container on the host.

## 75. Common Misconceptions

### Misconception 1: A program and a process are the same

A program is stored code; a process is a running instance with state and resources.

### Misconception 2: Threads are isolated like processes

Threads share process memory and can corrupt one another's state.

### Misconception 3: Containers have their own kernel

Containers share the host kernel.

### Misconception 4: High load always means high CPU use

Blocked I/O tasks can increase load without consuming much CPU.

### Misconception 5: Restarting a service fixes the root cause

A restart may restore service temporarily while hiding leaks, deadlocks, or resource exhaustion.

## 76. Architect's Mental Model

For any operating-system problem, ask:

1. Which process or thread is affected?
2. What state is it in?
3. Is the bottleneck in user space or kernel space?
4. Which system calls or resources are involved?
5. Is the task CPU-bound, blocked, or waiting on a lock?
6. Are file descriptors, sockets, PIDs, or memory exhausted?
7. Which privileges and security boundaries apply?
8. Is the workload constrained by cgroups or namespaces?
9. Is the issue inside the guest, container, or host kernel?
10. What evidence will confirm the root cause?

## 77. Chapter Summary

- The operating system abstracts hardware and manages shared resources.
- The kernel runs with broad privilege; applications run in restricted user space.
- System calls provide controlled access to kernel services.
- A process is a running program with resources; threads are schedulable execution units that share process state.
- Schedulers manage runnable work, priorities, affinity, and preemption.
- Context switches, interrupts, system calls, and synchronization affect performance.
- Files, descriptors, sockets, pipes, and IPC are kernel-managed abstractions.
- Containers use namespaces and control groups but share the host kernel.
- Virtual machines run separate guest kernels on virtual hardware.
- Operating-system troubleshooting requires process state, resource, system-call, kernel, and host-layer evidence.
