# Chapter 3.6 — Routing, Routers and Layer 3 Packet Forwarding

## Chapter Goal

Layer 2 communication works only inside a single broadcast domain. The moment communication must cross subnet boundaries, Layer 3 takes over.

Routers are responsible for moving packets between networks. Every cloud provider, enterprise network and Kubernetes cluster ultimately relies on routing.

This chapter explains how routers make forwarding decisions and how packets travel from one network to another.

## Learning Objectives

After completing this chapter you will be able to:

- Explain routing.
- Understand router architecture.
- Read routing tables.
- Explain longest prefix matching.

## 3.6.1 Why Routing Exists

Consider two computers on the same subnet:

```text
Server A (192.168.10.15)
        |
      Switch
        |
Server B (192.168.10.20)
```

Communication occurs directly through Layer 2.

Now consider two systems on different networks:

```text
Server A (192.168.10.15)
        |
      Router
        |
Server C (10.20.30.40)
```

A router is required because the destination is outside the source subnet.

## 3.6.2 What Is a Router?

A router is a Layer 3 device that forwards packets between different IP networks.

It evaluates:

- Destination IP address
- Routing table
- Most specific matching route
- Next hop
- Outgoing interface

The routing decision is based on IP prefixes, not destination MAC addresses.

## 3.6.3 Router Responsibilities

A router performs:

- Packet forwarding
- Route selection
- Network segmentation
- Broadcast-domain separation
- Path optimization
- TTL processing

## 3.6.4 Router Interfaces

Each router interface belongs to a network.

```text
Router
├── eth0: 192.168.10.1/24
└── eth1: 10.1.0.1/16
```

A router can forward packets between the connected networks when forwarding is enabled and policy allows it.

## 3.6.5 Default Gateway

A host uses its default gateway for destinations outside its local subnet.

Example:

```text
Host:    192.168.1.25/24
Gateway: 192.168.1.1
```

The gateway must be reachable on the host's local Layer 2 network.

## 3.6.6 Local Versus Remote Destination

Before transmitting, a host compares the destination address with its own subnet.

```text
Destination local?
├── Yes: resolve destination MAC and send directly
└── No:  resolve gateway MAC and send to default gateway
```

The final destination IP remains in the IP packet. The Ethernet destination is the next-hop MAC address.

## 3.6.7 Packet-Forwarding Workflow

Example path:

```text
Client 192.168.1.20
        |
Gateway 192.168.1.1
        |
Intermediate routers
        |
Server 10.10.5.40
```

Process:

1. The application generates data.
2. The transport layer creates a segment or datagram.
3. IP creates a packet containing source and destination IP addresses.
4. The host determines that the destination is remote.
5. ARP resolves the gateway's MAC address.
6. The host sends an Ethernet frame to the gateway.
7. The router removes the incoming frame header.
8. The router performs a routing-table lookup.
9. The router selects a next hop and outgoing interface.
10. The router creates a new Layer 2 frame for the next link.
11. The process repeats until the destination network is reached.

## 3.6.8 Re-encapsulation at Every Hop

The IP packet normally keeps the same source and destination IP addresses across the path, excluding mechanisms such as NAT.

The Layer 2 frame changes at every routed hop:

```text
Incoming frame
      |
IP packet extracted
      |
Routing decision
      |
New outgoing frame
```

Routers therefore connect Layer 2 segments while forwarding Layer 3 packets.

## 3.6.9 Routing Table

A routing table maps destination prefixes to forwarding actions.

| Destination | Next Hop | Interface |
|---|---|---|
| 192.168.1.0/24 | Directly connected | eth0 |
| 10.10.0.0/16 | 172.16.1.2 | eth1 |
| 0.0.0.0/0 | 203.0.113.1 | eth2 |

View the Linux IPv4 routing table:

```bash
ip route
```

Example:

```text
default via 192.168.1.1 dev eth0
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.25
10.20.0.0/16 via 192.168.1.254 dev eth0
```

## 3.6.10 Connected Routes

Assigning an address to an interface normally creates a connected route.

For example:

```text
eth0 = 192.168.10.20/24
```

produces a route for:

```text
192.168.10.0/24 dev eth0
```

Connected routes indicate that the destination can be reached directly on a local link.

## 3.6.11 Static Routes

A static route is configured manually.

```bash
sudo ip route add 10.50.0.0/16 via 192.168.1.254
```

Delete it:

```bash
sudo ip route del 10.50.0.0/16
```

Static routes are predictable but require manual maintenance.

## 3.6.12 Default Route

The default route is represented by:

```text
0.0.0.0/0
```

It matches any IPv4 destination for which no more-specific route exists.

```bash
ip route show default
```

A missing or incorrect default route commonly causes this pattern:

- Local subnet communication works.
- Remote network or Internet access fails.

## 3.6.13 Longest Prefix Match

A destination may match several routes.

```text
10.0.0.0/8
10.10.0.0/16
10.10.20.0/24
```

For destination `10.10.20.15`, the router selects `10.10.20.0/24` because `/24` is the longest and therefore most specific matching prefix.

Preference by specificity:

```text
/32 > /24 > /16 > /8 > /0
```

The route source or metric is considered only when routes have equivalent destination specificity under the platform's selection rules.

## 3.6.14 Next Hop

The next hop is the next router toward the destination.

```text
Destination: 10.20.30.0/24
Next hop:    192.168.1.254
```

The next-hop address must itself be reachable through a connected or otherwise resolvable route.

Inspect the exact route Linux would use:

```bash
ip route get 10.20.30.40
```

## 3.6.15 Static Routing

Advantages:

- Simple for small networks
- Predictable
- No routing-protocol traffic
- Useful for default, host and exceptional routes

Limitations:

- Manual maintenance
- Poor scalability
- No automatic topology adaptation
- Higher operational risk during changes

## 3.6.16 Dynamic Routing

Dynamic routing protocols exchange reachability information and adapt to topology changes.

Examples:

- OSPF
- IS-IS
- BGP
- RIP

Dynamic routing does not replace the routing table; it is one mechanism used to populate it.

## 3.6.17 Route Summarization

Several contiguous networks can sometimes be represented by one aggregate prefix.

Instead of:

```text
10.1.0.0/24
10.1.1.0/24
10.1.2.0/24
10.1.3.0/24
```

advertise:

```text
10.1.0.0/22
```

Benefits include:

- Smaller routing tables
- Reduced update volume
- Improved scalability
- Failure containment when designed correctly

An inaccurate summary can attract traffic for networks that do not exist, so aggregation must follow binary prefix boundaries.

## 3.6.18 Routing Loops and TTL

A routing loop occurs when routers forward packets in a cycle.

```text
Router A -> Router B -> Router C -> Router A
```

IPv4 uses the Time To Live field to prevent indefinite circulation.

Each router decrements TTL by one. When TTL reaches zero, the router discards the packet and normally returns ICMP Time Exceeded.

This behavior enables tools such as `traceroute` and `tracepath`.

## 3.6.19 Linux as a Router

Check IPv4 forwarding:

```bash
sysctl net.ipv4.ip_forward
```

Enable it temporarily:

```bash
sudo sysctl -w net.ipv4.ip_forward=1
```

Persist it through an appropriate file under `/etc/sysctl.d/`, for example:

```text
net.ipv4.ip_forward = 1
```

Then apply the configuration:

```bash
sudo sysctl --system
```

Enabling forwarding alone does not create correct routes, firewall policy or NAT rules. Those must be designed separately.

## 3.6.20 Routing in AWS

AWS route tables associate destination CIDRs with targets such as:

- Local VPC routing
- Internet Gateway
- NAT Gateway
- Transit Gateway
- Virtual Private Gateway
- VPC peering connection
- Network interface

The underlying logic remains destination-prefix matching and route selection.

## 3.6.21 Routing in Kubernetes

A typical Pod packet may traverse:

```text
Pod network namespace
      |
Virtual interface
      |
Linux host routing
      |
CNI data plane
      |
Destination node or Pod
```

The implementation varies by CNI plugin, but Linux routes, interfaces, neighbor resolution and packet filtering remain fundamental.

## Production Best Practices

- Keep routing design intentional and documented.
- Prefer summarizable address allocation.
- Verify return-path routing, not only the forward path.
- Avoid overlapping CIDR blocks.
- Monitor route changes in dynamic environments.
- Validate next-hop reachability.
- Use the most specific route only when its operational purpose is clear.
- Treat default routes as high-impact configuration.

## Production Troubleshooting

### Cannot Reach a Remote Network

```bash
ip addr
ip route
ip route get <destination>
ping <gateway>
tracepath <destination>
```

Validate:

- Correct local prefix
- Correct default or specific route
- Reachable next hop
- Return path from destination
- Firewall and security policy

### Wrong Route Selected

Examine:

```bash
ip route get <destination>
ip route show table all
```

Check:

- More-specific routes
- Policy routing rules
- Route metrics
- Multiple routing tables
- Stale configuration

### Missing Default Gateway

Symptom:

- Local subnet works
- Remote connectivity fails

Check:

```bash
ip route show default
```

### Routing Loop

Symptoms:

- Repeated hops
- TTL exceeded
- High latency or packet loss

Use:

```bash
traceroute <destination>
tracepath <destination>
```

### Asymmetric Routing

The forward and return packets take different paths. This can be valid, but stateful firewalls, NAT devices or strict reverse-path filtering may reject the traffic.

Inspect:

```bash
ip route get <destination>
ip rule
sysctl net.ipv4.conf.all.rp_filter
```
